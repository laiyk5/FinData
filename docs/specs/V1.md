# v1 implementation specification

This specification records concrete encodings for the behavioral contracts in the six primary documents. It does not redefine those contracts.

## Workspace layout

`workspace.json` contains `workspace_version: 1`. `token`, `config.json`, and runtime discovery file `server.json` use mode `0600`; the workspace uses `0700`. `server.lock`, `config.lock`, `events.lock`, provider limiter locks, and per-dataset `gate.lock` files are POSIX advisory locks.

Each `datasets/<name>/` contains `gate.lock` and one mode-`0600` `dataset.duckdb`. There are no
generation or snapshot directories. Registration creates the database through a same-filesystem
temporary file and atomic replacement.

Every dataset database contains:

- `data`, whose columns exactly match the registered logical Arrow schema;
- `_findata_coverage`, whose partition-key columns use their registered DuckDB types and are followed
  by `start_date DATE` and `end_date DATE`; the partition-key tuple is logically unique, and the
  table is empty for a non-coverage dataset; and
- `_findata_metadata`, exactly one row containing dataset name, storage-adapter version `1`,
  data-layout version, encoded Arrow schema, declared keys, missing-data policy, `state`, unsigned
  integer `revision`, opaque publication ID, and DuckDB storage-compatibility value.

An initialized database starts with `state = 'uninitialized'`, `revision = 0`, and no publication
ID. Each committed checkpoint batch updates data, coverage, state, revision, and publication ID in
one DuckDB transaction. The publication ID remains an opaque current-revision identifier and does
not imply that an older revision can be opened.

Provider fetch and Arrow validation occur outside the database gate. A writer acquires the exclusive
gate before opening a read/write connection and closes the connection before releasing it. DataLoader
does the symmetric operation with a shared gate and read-only connection. Task-local validated inputs
may use operating-system temporary storage, but no temporary input is reader-visible or durable until
the transaction commits.

`config.json` is one atomic JSON object containing `config_version: 1`, a monotonically increasing
integer `revision`, and a `values` map. Every successful set or unset increments the revision.
Secret keys are redacted by the API. Cron state is stored under `cron.jobs`; rate-bucket state uses
provider-private files.
`display.timezone` is an IANA timezone name used only by human presentation and defaults to `UTC`;
invalid timezone names are rejected when configuration is written.

Keys under `dataset.<dataset-name>.*` are resolved to the registered dataset plugin. Each plugin
declares its allowed keys as JSON Schemas and supplies normalization, help, and update-readiness
evaluation. A configuration mutation validates and normalizes the complete candidate value before
the single atomic replacement; an unknown dataset, unknown setting, or invalid value returns `400`
and leaves the previous object unchanged. The core treats the normalized JSON as opaque.

Normalization is deterministic and performs no external request or task submission. It may inspect
only committed data from a dependency declared by the plugin, through the public DataLoader. An
uninitialized required reference dataset returns `400` with the exact
`tushare_index_basic complete` operation needed to initialize it.
Unsetting a recognized key is valid even when it makes `update` unready; readiness is a scheduling
and submission precondition, not a configuration-storage constraint.

Every task execution records the configuration revision and receives one immutable snapshot of its
plugin settings. Parameterless `update` and cron readiness use that snapshot together with the
committed dataset state captured when the execution begins. Dataset-specific
syntax, including Tushare constituent selectors, is specified by the owning plugin in
[DATASETS.md](../DATASETS.md), not by this core protocol.

## Task persistence and process channel

Handle and execution records are separate atomic JSON files under `tasks/handles` and `tasks/executions`. Logs are append-only JSON Lines under `tasks/logs`. IDs are random hexadecimal UUIDs and timestamps are Unix seconds.

Each spawned task connects to a unique `multiprocessing.connection` listener bound to localhost with a random 256-bit authentication key. Child-to-server messages cover logs, progress, public state, work-item liveness, dependency requests, and terminal results. Server-to-child messages cover cancellation and dependency results. The authentication key is process-lifetime-only and is not persisted.

The plugin exposes deterministic, independently committable work items. A complete-table replacement
is one indivisible item; registered key/time-range replacements may be separate items. The initial
checkpoint-batch limits are 60 seconds of provider work, 64 completed provider requests, or 256 MiB
of validated Arrow input, whichever boundary is observed first between items. An item that crosses
one or more limits forms one oversized batch rather than being split unsafely. Operation completion
also closes a nonempty batch. Empty work creates no transaction unless coverage or initialization
state must change. Tests may lower these limits explicitly; production behavior never infers a
checkpoint from one provider request. A failed or canceled uncommitted batch is discarded and
reconstructed from the last committed coverage on rerun.

## Events and cron

`events.jsonl` is append-only. Primary records contain an ID, Unix timestamp, kind, severity, message, and context. Acknowledgements are new records whose `reference` names the primary event.

Cron uses five-field expressions and IANA timezone names. Persisted jobs contain enabled state, suggested or overridden expression/timezone, last run, next run, and last evaluation time. Stored instants are timezone-aware ISO 8601 values in UTC.

## HTTP API

All routes are under `/v1`, bind to localhost, accept and return JSON, and require `Authorization: Bearer <workspace-token>`.

The `<id>` operand on task status, logs, and cancel routes, and the event ID supplied to
`/events/ack`, accepts either a full identifier or a lowercase hexadecimal prefix of at least eight
characters. Resolution is atomic against retained identifiers. Exact match takes precedence; an
invalid or too-short prefix returns `400`, no match returns `404`, and multiple matches return `409`
without side effects. Successful responses contain the full resolved identifier. Task routes
resolve handle IDs only and never execution IDs. No other v1 resource ID supports prefix matching.

## CLI structured records

`--format json` emits one command-result object to stdout, or one `error` object to stderr on
failure. It does not stream. `--format jsonl` emits one object per line and every object has a
`type` discriminator:

- `task.accepted` contains the submitted handle and execution identity;
- `task.log` contains `message`;
- `task.diagnostic` contains `handle_id`, `severity` (`warning` or `error`), stable `code`, `message`,
  optional `context`, and positive integer `count` (default `1`);
- `task.progress` contains `handle_id`, public `status`, optional `stage`, optional `reason`, and
  optional `progress`;
- `task.result` contains the terminal handle record; and
- `error` contains a sanitized `error` message.

The terminal handle record includes `diagnostic_counts: {warning, error}` when either count is
nonzero. JSONL emits each diagnostic received from the server. Exact repeated diagnostics may be
aggregated into one record only when `count` preserves their number of logical occurrences; the
human renderer's visibility limit never removes or reduces structured records.

Public task records may contain `stage`, `progress: {current, total}`, and `reason`. `stage` names
server-reported work such as `fetching:<dataset>` or `committing:<dataset>`. Progress may additionally
contain `checkpointed`, never greater than `current`, to distinguish processed from durably committed
work. `reason` is present only
while waiting and identifies a semantic gate such as `provider_rate_limit` or
`dependency:<dataset>`; it is cleared on running and terminal transitions. New optional fields may
be added in a compatible v1 release, but existing field meanings and record types do not change.

- `/system/status`
- `/tasks`, `/tasks/<id>`, `/tasks/<id>/logs`, `/tasks/<id>/cancel`
- `/datasets`, `/datasets/<name>`, `/datasets/<name>/reset`, dataset operations, and status routes
- `/providers`, `/providers/tushare`, `/providers/tushare/check`
- `/cron` and per-dataset enable, disable, schedule, and reset routes
- `/events` and `/events/ack`
- `/config` and `/config/<key>`

Bad syntax or contract validation returns `400`; authentication failure returns `401`; an unknown retained task returns `404`; queue rejection returns `409`; unexpected failures return `500`. Task submission returns `202` with a handle ID.

`POST /datasets/<name>/reset` requires `{"confirm": true}`. Missing confirmation returns `400`;
queued or active work for that dataset returns `409`. A successful reset acquires the task mutex and
exclusive gate, replaces only that database with a valid uninitialized database, and returns the new
state. Configuration, settings, task records, and other dataset databases are unchanged.

## Compatibility

Readers reject unknown storage-adapter, DuckDB-storage, or data-layout versions without writing.
Startup recovery, after acquiring the workspace server lock, kills only a process whose PID and
recorded process-start value both match, marks active records interrupted, removes Findata-owned
abandoned temporary inputs, and lets DuckDB recover each database through its supported APIs. Findata
never unlinks a DuckDB WAL directly. Ordinary startup and updates do not copy the complete database
or retain historical revisions.
